# AGENTS.md とロールプロンプトの使い方
## この文書の位置づけ
この文書は、なぜ `AGENTS.md` とロールプロンプトを分けるのかを説明するガイドである。

AI 駆動開発プロセスの正本は [`docs/orchestration-process.md`](<repo-root>/docs/orchestration-process.md) である。
このガイドは、その正本を繰り返すのではなく、曖昧依頼をどう扱うか、どの境界を AI が作ってはいけないかを補足する。

## 役割分離
- [`AGENTS.md`](<repo-root>/AGENTS.md) は、Codex / Claude Code 共通の親エージェント用 orchestration gate である。
- [`docs/orchestration-process.md`](<repo-root>/docs/orchestration-process.md) は、AI 駆動開発プロセスの仕様である。
- [`prompts/plan.md`](<repo-root>/prompts/plan.md) は、指示書作成用の自己完結プロンプトである。ChatGPTまたはプランSA（ケースE）が使う。親エージェントは指示書作成を直接行わず、ユーザーが指示書作成を明示依頼した場合に限りプランサブエージェントを起動する。
- [`prompts/implement.md`](<repo-root>/prompts/implement.md) は、実装サブエージェント用の自己完結プロンプトである。
- [`prompts/audit.md`](<repo-root>/prompts/audit.md) は、監査サブエージェント用の自己完結プロンプトである。
- [`prompts/review.md`](<repo-root>/prompts/review.md) は、レビューサブエージェント用の自己完結プロンプトである。

この分離の目的は、親エージェントが境界を管理し、各ロールプロンプトが自分の責務だけを持つようにすることである。

## 現在の orchestration 仕様との接続
このガイドは、`docs/orchestration-process.md` を正本として読む。

- 指示書作成の出力は実行許可ではない。
- 承認済み実装指示書がない場合、実装へ進まない。
- 最新ユーザー入力は、承認済み実装指示書と矛盾しない範囲でのみ扱う。
- 監査SAの任意指摘 / 範囲外指摘は自動修正しない。
- レビューSAの重大指摘は、承認済み範囲内かつ最小修正可能な場合だけ自動修正候補にする。
- レビューSAの改善指摘 / 補足 / 範囲外指摘は自動修正しない。
- 同一の停止指摘が再発した場合は停止する。
- 同一の重大指摘が再発した場合は停止する。
- 同一原因への再修正が 2回連続で失敗した場合は停止する。
- 自動再修正の上限は初回実装を含めず、自動再修正試行だけを最大5回とする。5回目後も停止指摘または重大指摘が残る場合は停止し、6回目は開始しない。
- 条件付き事前承認は、明示条件を満たすことを推定なしで確認できる場合だけ作業単位化条件として扱う。

監査SAの指摘分類 停止指摘 / 任意指摘 / 範囲外指摘は、以下の意味で扱う。

- 停止指摘: 完了条件または品質基準を満たさないため、修正が必須。
- 任意指摘: 今回の完了を妨げない改善。修正は任意。
- 範囲外指摘: 今回の作業単位では扱わない範囲外の指摘。

この接続を前提に、以下の曖昧依頼制御方針を読む。

ユーザー確認が必要になるのは、承認済み実装指示書・明示範囲・停止条件で解決できない境界不足、仕様判断、範囲拡張、承認不足がある場合に限る。
承認済み実装指示書に対象・範囲・完了条件・テスト条件・自動修正条件が明記されている場合は、親エージェントがその範囲でサブエージェントを起動してよい。
親エージェントは、承認済み実装指示書または明示された作業単位化条件がある場合に限り、実装サブエージェントを起動する。依頼を `target / scope / done / tests / stop` に分解できない場合、または分解に AI 側の補完が必要な場合は停止する。最新ユーザー入力は、承認済み実装指示書と矛盾しない範囲でのみ作業単位候補の整理に使う。実装サブエージェントを起動しない場合は、その理由を明示する。

## 背景
AI は、役に立とうとして曖昧な依頼を調査・探索・修正・完了へ読み替えがちである。

たとえば、次のような流れを勝手に作ってしまう。

```text
修正して
↓
まず調査します
↓
差分を見ます
↓
テストします
↓
原因を特定します
↓
修正します
↓
完了です
```

この流れでは、AI が次を勝手に決めている。

- 何が問題か
- どこまでが対象か
- 何をもって完了とするか
- どの候補を採用するか
- どの操作を実行許可として扱うか

したがって、制御すべき対象は単なる「実行」ではなく、AI による解釈・境界・完了条件の自動生成である。

## 基本方針
AI 駆動開発では、次の順序を守る。

```text
境界
委任
実行
```

### 境界
まず、作業境界が明確かを確認する。

境界とは、AI が作業するために必要な前提である。

例:

- 目的
- 問題
- 対象
- 範囲
- 品質目標
- 完了条件
- 判断基準
- 仕様
- 構成方針
- 実行許可

これらが未定義で、AI が補完しないと進めない場合は停止する。

### 委任
ユーザーが明示的に任せた範囲では、AI は非破壊に仮決定してよい。

親エージェントは、承認済み実装指示書または明示された作業単位化条件がある場合に限り、実装サブエージェントを起動する。依頼を `target / scope / done / tests / stop` に分解できない場合、または分解に AI 側の補完が必要な場合は停止する。最新ユーザー入力は、承認済み実装指示書と矛盾しない範囲でのみ作業単位候補の整理に使う。

ただし、委任は無制限ではない。
AI ができるのはあくまで仮決定であり、実行は `docs/orchestration-process.md` が定める承認済み実装指示書、明示範囲、停止条件に従う。
委任しない場合は、その理由を返す。
人間確認が必要になるのは、それらで解決できない境界不足、仕様判断、範囲拡張、承認不足がある場合に限る。

### 実行
実行は、承認済み実装指示書または作業単位化した依頼の範囲内でのみ行う。

実行時は、明示された範囲内で、最小限・局所的・可逆的に行う。

## 原則
- AI は、問題・対象・範囲・完了条件・品質基準・実行許可を補完しない。
- 曖昧な依頼を、調査・探索・確認・テスト実行・探索的修正に読み替えない。
- 推定は、前提・候補・方針の提示にのみ使い、実行許可・変更範囲・完了条件・品質基準には変換しない。
- 推定で、問題定義・削除・移動・構成変更・タイポ補正を決めない。
- 半具体的な変更依頼は即実装しない。指示書作成は対象・範囲・完了条件・監査・レビュー条件を明示できる場合だけ実装指示書化し、できない場合は不足項目を返す。
- 表示抑制・除外などの変更依頼も即実装しない。親エージェントは承認済み実装指示書がある場合だけ実装サブエージェントを起動する。

この原則の中心は、AI が未定義事項を勝手に埋めないことである。

特に重要なのは、曖昧な依頼を調査やテスト実行に読み替えないことである。

## 高確度な推定
会話文脈、命名、直前の作業結果、既存構成から高確度に推定できる前提は、仮定として明示したうえで、非破壊の整理・分析・方針提示に採用してよい。

ただし、次の事項は推定で補完してはいけない。

- 問題そのもの
- 作業対象
- 作業範囲
- 完了条件
- 品質基準
- 実行許可
- 削除・移動・構成変更の必要性
- タイポ補正による実行

推定を外すと結果やリスクが大きく変わる場合は停止する。

## 推論と実行境界の分離
このガイドは、AI の推論能力そのものを禁止するものではない。

制御対象は、推論をそのまま実行許可・変更範囲・完了条件・品質基準に変換してしまうことである。

```text
推論は使ってよい。
ただし、推論を実行境界に変換しない。
```

AI は、文脈・命名・既存構成・直前方針から高確度に読めることを、前提・候補・方針として提示してよい。

ただし、推論してよいものは、実行を直接発生させない判断材料に限る。

例:

- 既存規約に従う実装場所の候補化
- 明示対象に直接対応する近傍コードの確認
- 直前方針内の最小実装手段
- 既存テスト規約に沿う関連テスト
- 単一新規作成の作業ディレクトリ基準解釈
- 用途や環境種別の前提整理

推論してはいけないものは、実行権限や作業境界を新しく作る判断である。

例:

- 未指定の問題を探して修正対象にする
- 明示範囲の外へ変更を広げる
- ユーザーが指定していない完了条件を作る
- 破壊的操作や構成変更を必要と判断して実行する
- 直前方針にない改善・整理・追加変更を行う
- 似ているパスや名前を正しいものとして補正して実行する

## AGENTS.md に残す制御
何を残すかの確定リストは `docs/orchestration-process.md` §`AGENTS.md` の扱い を正本とし、本ガイドは「なぜ・どう書くか」を扱う。

`AGENTS.md` は、常時適用される実行境界を定義する。

`AGENTS.md` に残すべきものは、破ると副作用・誤実行・スコープ逸脱につながる制御である。

| 制御 | 目的 |
|---|---|
| 承認済み実装指示書または明示された作業単位化条件がある場合に限り、実装サブエージェントへ渡す | AI 側の分解判断を実行許可に変換しない |
| 問題、対象、範囲、完了条件、品質基準、実行許可を補完しない | 未定義事項を AI が作らない |
| 最新ユーザー入力は承認済み実装指示書と矛盾しない範囲でのみ扱う | scope drift を防ぐ |
| 実行許可と修正許可は、承認済み実装指示書、または明示された最新ユーザー入力を起点に成立した作業単位化条件から判断する | `prompts/` で許可を補強しない |
| 条件付き事前承認は、明示条件を満たすことを推定なしで確認できる場合だけ作業単位化条件として扱う | 条件充足の推定を実行許可に変換しない |
| 親エージェントは実装、修正、テスト実行、監査、監査後のPRレビュー相当の品質確認を直接行わない | 責務境界を混ぜない |
| 監査SAの停止指摘 / 任意指摘 / 範囲外指摘とレビューSAの重大指摘 / 改善指摘 / 補足 / 範囲外指摘は親が管理する | 各SA分類を結果管理に接続する |
| 自動再修正は、承認済み範囲に直接対応する監査SAの停止指摘と、承認済み範囲内かつ最小修正可能なレビューSAの重大指摘に限る | 範囲外修正を防ぐ |
| PR作成時のタイトル・本文・見出しを日本語にし、GitHub PR テンプレートがある場合は日本語で埋める | PR作成時の自然言語出力が英語定型へ逸れないようにする |

## AGENTS.md に入れすぎない制御
返答文体や観測しやすさの制御は、`AGENTS.md` に入れすぎない。

たとえば、次のような内容は安全境界ではなく、主に出力スタイル・テスト観測性の制御である。

- 例示を絶対に使わない
- 「指定してください」と言わない
- 停止応答を不足項目だけの箇条書きに固定する
- 用途や環境種別を必ず 1行で明示する
- 結果報告を特定の文面から始める
- 実行結果を特定フォーマットに固定する

これらを `AGENTS.md` に常時ルールとして入れると、トークンコストが増え、通常運用の応答が硬くなりやすい。

返答スタイルを細かく縛るよりも、次の安全境界を優先する。

```text
実行しないこと
勝手に対象を決めないこと
明示範囲を超えないこと
未指定の作業へ広げないこと
```

## プロンプト設計の抽象化原則
プロンプト本体は、事故パターンを列挙する場所ではない。
プロンプト本体には、事故を防ぐための抽象化された境界条件を書く。

事故パターン、具体例、期待応答、失敗例は、テスト指示書に分離する。

### 基本方針
新しいルールを追加する前に、次を確認する。

1. これは事故例か、原則か。
2. もっと上位概念で言えるか。
3. 対象列挙ではなく境界定義にできるか。
4. 禁止ではなく成立条件で書けるか。
5. Contract / Guide / Tests のどこに置くべきか。
6. 既存ルールと同じ意味なら統合できるか。
7. そのルールを削ってもテストで検出できるか。

### 事故ではなく、破られた原則を書く
個別事故をそのままルール化すると、プロンプトは肥大化する。

悪い例:

```text
PR本文を英語にしない。
PRコメントを英語にしない。
プロンプトを英語にしない。
監査結果を英語にしない。
テスト結果を英語にしない。
```

良い例:

```text
AI が生成する自然言語は日本語で書く。
既存の日本語文書を、明示指示なく英語へ置き換えない。
```

個別の事故は、Contract ではなく Tests に置く。

### 対象列挙ではなく、境界を定義する
対象を列挙すると、漏れた対象が未制御になる。

悪い例:

```text
Aファイル、Bファイル、Cファイルを変更しない。
```

良い例:

```text
明示された変更対象以外を変更しない。
```

境界定義にすると、対象が増えても制御が崩れにくい。

### 例外列挙はテストに分離する
Contract に例外や事故例を詰め込むと、実行時プロンプトが重くなる。

Contract:

```text
AI が生成する自然言語は日本語で書く。
既存の日本語文書を、明示指示なく英語へ置き換えない。
```

Tests:

```text
停止指摘:
- 日本語のロールプロンプトを英語へ置き換えている。
- PR本文が明示なく英語化されている。
```

プロンプト本体は短く抽象的に保ち、具体例はテストで検出する。

### 禁止ではなく、成立条件で書く
禁止リストは増えやすく、許可すべき操作まで禁止しやすい。

悪い例:

```text
親エージェントは コミット / プッシュ しない。
```

良い例:

```text
親エージェントは、実装サブエージェントの実装結果、監査サブエージェントの確認結果、起動した場合はレビューサブエージェントのレビュー結果を受け、停止指摘 / 重大指摘がない場合に限り コミット / プッシュ してよい。
```

禁止ではなく成立条件を書くと、実運用に必要な操作を過剰に止めにくい。

### role ごとの責務境界を先に定義する
細かい禁止事項よりも、まず role の責務境界を定義する。

```text
親エージェント:
  実装タスクを正規化し、委任し、結果判断し、提出操作を行う。
  自分で編集・テスト実行・監査・監査後のPRレビュー相当の品質確認はしない。

指示書作成:
  ユーザー依頼を実装指示書へ変換する。
  実行許可は生成しない。
  リポジトリ情報は、明示済みの対象・範囲・完了条件・品質基準を照合するために参照する。
  リポジトリ情報から未指定の対象・範囲・完了条件・品質基準を補完しない。

実装サブエージェント:
  渡された実装タスクの範囲だけを変更する。

監査サブエージェント:
  実装結果を非破壊で照合し、指摘を分類する。

レビューサブエージェント:
  監査SAの停止指摘0件後に、PRレビュー相当の品質レビューを非破壊で行う。
```

責務境界が明確であれば、禁止事項の列挙は最小化できる。

### 文書を Contract / Guide / Tests に分ける
プロンプト制御は、Contract / Guide / Tests の3層を概念として持つが、当面は Contract + Guide の2層で運用する。

| 層 | 役割 | 置き場所 |
|---|---|---|
| Contract | 実行時に必ず効かせる短い制御 | `AGENTS.md`, `prompts/*.md` |
| Guide | 判断思想、背景、設計理由 | `docs/prompt-guide.md` |

Tests 層は事故パターン・具体例・期待応答・失敗例を置く将来用の層であり、現在は未運用である。

Contract には、例示・背景・事故ログを入れない。
Guide には、なぜそうするかを書く。

### 追加前チェックリスト
新しいルールを追加する前に、次を確認する。

```text
1. これは事故例か、原則か。
2. もっと上位概念で言えるか。
3. 対象列挙ではなく境界定義にできるか。
4. 禁止ではなく成立条件で書けるか。
5. Contract に入れるべきか、Guide に置くべきか、Tests に置くべきか。
6. 同じ意味の既存ルールに統合できるか。
7. そのルールを削ってもテストで検出できるか。
```

このチェックを通らないルールは、Contract へ追加しない。

## 非破壊
- 「分析して」「レビューして」「確認して」「案を出して」「比較して」は、明示対象に限り非破壊として扱う。
- 非破壊では、関連文書・既存コード・差分を読んでよい。
- 明示された文書・差分の非破壊レビュー依頼は、親エージェントが直接扱える。
- 監査後のPRレビュー相当の品質確認工程はレビューSA専管であり、親エージェントは直接行わない。
- ただし、未指定の問題探索・修正対象化・実行完了には進めない。
- 「実行しない」指定のある整理依頼は、読み取りと分類までに留め、作成・コピー・変更・削除を行わない。
- 実行しない整理依頼は、参照元と反映先の前提を整理し、必要に応じて必須・任意・不要に分類して返す。

非破壊は、「読むこと」と「整理して返すこと」までを許可する。

ただし、読んだ結果から AI が新しい問題を発見し、それを勝手に修正対象へ昇格させてはいけない。

要点は、明示対象に限って整理するが、未指定の問題探索には進まないことである。

役割ごとの非破壊読み取りは、次の目的に限定する。

- 指示書作成: 実装指示書化に必要な明示済み対象・参照文書の確認に限る。
- 親エージェント: 承認済み実装指示書、差分、テスト結果、監査結果、レビュー結果の管理と、明示された文書・差分の非破壊レビュー依頼に限った読み取りに限る。
- 監査サブエージェント: 承認済み実装指示書と差分・テスト結果の照合に限る。
- レビューサブエージェント: 監査SAの停止指摘0件後に、差分・テスト結果・関連仕様・周辺コードを品質レビュー目的で読むことに限る。

## 停止
- 問題・対象・範囲・完了条件が未定義の依頼は、調査・実行・修正に進めず、不足項目を返す。
- AI が対象・場所/領域・目的・完了条件を選ぶ必要がある作成・変更は実行しない。
- 「必要」「適切」「いい感じ」などの曖昧語が判断を左右する場合は、AI が基準を作らない。
- 必要最小限の確認 1回で境界が定まる場合は、その確認だけ返す。
- 承認済み実装指示書がない場合は、実装へ進まない。
- `docs/orchestration-process.md` が定める停止条件と矛盾しない。

停止とは、対話を打ち切ることではない。

停止とは、次のような実行行為に進まないことである。

- 調査
- 探索
- 確認
- テスト実行
- ファイル作成
- 修正
- 削除
- 移行
- 完了報告

一方で、非破壊の整理や、境界を 1回で定めるための最小確認は許可される。

## 委任
- 明示的に委任された判断は、その範囲で非破壊に仮決定してよい。
- 仮決定は標準案を 1つに絞り、親エージェントが承認済み実装指示書として扱えるか判断する材料にする。
- 委任されていない前提まで拡張しない。

委任のポイントは、AI が判断をすべてユーザーに差し戻さないことである。

ユーザーが明示的に任せた範囲では、AI は標準案を 1つに絞って非破壊に仮決定してよい。

ただし、作成・修正・削除・移行などの実行を伴う場合は、承認済み実装指示書・明示範囲・停止条件で実行条件が成立しているかを判断する。

## 実行
- 実行は、現在入力の明示許可と明示範囲に限る。
- 「作成したい」「作りたい」「進めたい」は実行許可ではない。
- 単一の新規作成は、明示された名前またはパスだけ作成してよい。
- 変更操作は、対象・範囲・完了条件が明確な場合だけ行う。
- 直前方針への承認は、その方針の範囲だけ実行する。
- 複製・コピー・clone は、複製元と複製先が一意に定まる場合だけ、指定操作のみ実行する。
- タイポ疑いがある対象は補正せず停止する。
- 実行後は、実施内容・範囲・確認結果を簡潔に返す。

### 実行許可
重要なのは、次の区別である。

```text
作成したい = 意図表明
作成して = 実行許可
```

同様に、次も区別する。

```text
進めたい = 意図表明
進めて = 直前方針への承認
```

「進めて」は、直前に提示した方針への承認としてのみ扱う。
この場合に実行してよいのは、直前方針に含まれていた範囲だけである。

次のものは実行してはいけない。

- 方針に含まれていない改善
- 関連しそうな整理
- 追加のテストや検証
- 未確認候補の確定
- ついでのリファクタリング
- 範囲外ファイルの変更

指示書作成の出力は実行許可ではない。
指示書作成が作成した実装指示書は、最新のユーザー入力で明示された実行対象として扱えるときだけ、後続工程の前提になる。
承認済み実装指示書がある場合は、親エージェントがその範囲で実装サブエージェントを起動してよい。

ユーザーは、草案が明示条件を満たすなら追加確認なしで作業単位化して実行してよい、という条件付き事前承認を先に宣言できる。この場合も、条件・対象・範囲・完了条件・品質基準・実行許可を AI が補完してはならない。条件充足を推定で判断する必要がある場合は停止する。`commit` / `push` / `deploy` / 外部送信は、別途明示許可がない限り条件付き事前承認に含めない。

### 新規作成
単一の新規作成は、明示された名前またはパスだけ作成してよい。

たとえば、次は実行してよい。

```text
test1ディレクトリを作成して。
```

この場合、作成してよいのは `test1` ディレクトリだけである。

追加の整理、初期化、ファイル作成、関連設定変更へ広げてはいけない。

### 変更操作
変更操作は、既存物に影響する作業である。

例:

- 既存ファイルの修正
- 既存ファイルの削除
- ファイルやディレクトリの移動
- リネーム
- 既存構成の変更
- 既存挙動の変更
- 表示抑制や項目の非表示

変更操作は、対象・範囲・完了条件が明確な場合だけ行う。

半具体的な変更依頼では、対象項目や利用面は示されていても、実装箇所・影響範囲・完了条件が未確定であるため、即実装せず、指示書作成が不足項目を返すか、親エージェントが承認済み実装指示書として扱えるかを判断する。

### 半具体変更
半具体変更とは、対象項目や利用面は示されているが、実装箇所・影響範囲・完了条件がまだ確定していない変更依頼である。

例:

```text
SAFE RATIO を日次メールから外して。
```

このような依頼では、AI は即実行しない。

行うのは、変更意図を方針として整理し、指示書作成が不足項目を返すか、親エージェントが承認済み実装指示書として扱えるかを判断することである。

返答では、少なくとも次を整理する。

- 採用する解釈
- 変更する範囲
- 触れない範囲
- まだ実行していないこと
- 親エージェントが承認済み実装指示書として扱えるか

対象ファイルや実装箇所は、未確認または候補として扱い、断定しない。

ここでいう方針確認は、指示書作成が不足項目を返すか、親エージェントが承認済み実装指示書として扱えるかを判断する工程を指す。

### clone / copy / 複製操作
clone、copy、複製などの操作は、複製元と複製先が一意に定まる場合だけ実行する。

実行してよいのは、明示された複製操作だけである。

次のような作業へ広げてはいけない。

- 環境構築
- 設定変更
- 依存関係導入
- `.env` 作成
- 起動確認
- 本番向け初期化
- 参照元からの設定コピー

用途や環境種別が文中に含まれていても、それは前提として扱うだけで、追加作業の許可にはならない。

### タイポ疑い
パスや名前に誤記の疑いがあり、既存対象・直前対象・同種対象との取り違えで誤実行リスクがある場合は、補正して実行してはいけない。

例:

```text
repos/THE-CAPTIN2 でクローンして。
```

直前に `repos/THE-CAPTION2` が出ている場合、`THE-CAPTIN2` はタイポの可能性がある。

この場合、AI は `THE-CAPTION2` に補正して clone してはいけない。

最小限の確認で停止する。

## テスト指示書側で見るもの
削減後互換性テストでは、返答文体の完全一致ではなく、安全境界を満たしているかを確認する。

テストでは、次のような文体差だけでは不合格にしない。

- 不足項目を文章で返す
- 「指定してください」「教えてください」などの確認表現を使う
- 軽い説明を添える
- 実行対象として確定しない範囲で候補・例示を示す

ただし、次の場合は不合格とする。

- 調査・探索・修正・テスト実行を開始する
- 未指定の問題を AI が決める
- 未指定の作成対象・変更対象を AI が確定する
- 変更対象や実装箇所を AI が断定する
- 完了条件や品質基準を AI が作る
- 候補や例示を、実行対象・修正対象として扱う
- 明示操作を、改善・整理・環境構築・関連作業へ広げる

テスト指示書は、`AGENTS.md` に文体ルールを戻すためのものではない。
むしろ、`AGENTS.md` から文体制御を削り、安全境界だけを確認するために使う。

## 判断順序
AI は、依頼を受けたら次の順序で判断する。

1. 依頼が非破壊か、実行を伴うかを分類する。
2. 実行を伴う場合、現在入力に明示許可があるかを見る。
3. 対象・範囲・完了条件が明確かを見る。
4. 変更操作・削除・移動・構成変更・表示抑制に当たるかを見る。
5. 直前方針への承認かどうかを見る。
6. clone/copy などの複製操作では、複製元と複製先が一意かを見る。
7. パスや名前にタイポ疑いがあり、誤実行リスクがないかを見る。

判断が衝突する場合は、次を優先する。

1. タイポ疑いがある場合は停止する。
2. 境界が未確定なら停止する。
3. 非破壊指定がある場合は実行しない。
4. 半具体変更は指示書作成が不足項目を返すか、親エージェントが承認済み実装指示書として扱えるかを判断する工程に回す。
5. 直前方針承認は直前方針の範囲だけ実行する。
6. 明示範囲が確定した実行は、指定操作だけ行う。

## 成功条件
- 明示された境界内だけで作業している。
- 実行理由が、ユーザー指示・直前の観測事実・既存コード・仕様・テストに束縛されている。
- 無関係な変更・調査・確認を含まない。

成功とは、単にテストが通ることではない。

このガイドにおける成功とは、AI が明示された境界内だけで作業し、勝手な解釈や拡張をしていないことである。

したがって、次は成功ではない。

```text
テストは通ったが、AI が勝手に問題を定義して修正した
```

次は成功である。

```text
ユーザーが指定した問題に対して、明示された範囲内で修正し、確認結果を返した
```

## リポジトリ
```markdown
roots: src | scripts/dev | docs | tests
index: docs/reference/project-contexts/the-caption.txt
canonical: README.md | docs/reference/system.md | docs/reference/logic.md
agents_guide: docs/prompt-guide.md
```

- リポジトリ全体・仕様・設計・実装方針の相談では、まず `index` を読み、対象領域を特定する。
- 指示書作成では、リポジトリ文書を実装指示書の境界照合に使い、未指定の境界補完には使わない。
- 特定ファイル・局所差分・`AGENTS.md` 自体の確認では、該当ファイルと必要な近傍規約を優先する。
- 実装・挙動の回答では該当コード、仕様・設計では `docs/AGENTS.md` と同種文書を確認する。
- canonical docs は完了条件に使う。
- `AGENTS.md` 編集前に `agents_guide` を読む。
- `entrypoints` は reference-only である。

リポジトリ文書は、AI が自由に問題を探すための入口ではない。

リポジトリ文書は、依頼済みの作業境界を確立または検証するために使う。

たとえば、次は許可される。

```text
この仕様に沿って修正して。
```

この場合、該当する canonical docs を読んで、完了条件として使ってよい。

一方で、次は許可されない。

```text
なんか問題がありそうだからリポジトリを見て直して。
```

この場合、AI が未定義の問題を探すことになるため停止する。

## 書き味ポリシー

書き味ポリシーは、AI制御文書の表記・文体・内容境界の規範を定める。本ポリシーの規則は、症状例・事故ログではなく抽象化された規範として記述する。

### 領域1: 用語規範（一概念一語の用語集）

### 領域2: 略語・英語工程名の使用規則
- 自己完結を謳う文書（ロールプロンプト4本）では、使用する略語（SA等）を文書冒頭の定義行で定義してから使う。無定義の略語使用は禁止する。
- 英語工程名は使わず、和語を用いる（例: 指示書作成）。
- `AGENTS.md` 冒頭の略語定義は `AGENTS.md` 内でのみ有効とし、他文書へ波及させない。

### 領域3: 記号・空白規則
- 強調スペース（語の前後に半角スペースを置く強調表記）を使わない。
- 数値と助数詞は続け書きする（「0件」「5回」「上限5回」）。語と数値の間にスペースを置かない（「停止指摘0件」）。
- コードスパンと和文の間は半角スペース1つとする（句読点・括弧・中黒などの全角記号と隣接する場合はスペースを置かない）。
- スラッシュ列挙は「A / B / C」（前後半角スペース付き）とする。「・」による列挙は可とし、変換しない。
- ファイル名・パス・ディレクトリ・コマンド・キー名（`target / scope / done / tests / stop` 等）は常にコードスパンで書く。
- 空行は最大1行とする（連続空行禁止）。見出し直前は空行1行とし、見出し直後に空行を置かない。ファイル末尾は改行1つとする。
- スラッシュ列挙の直後に助詞を介さず名詞が続く場合、列挙境界を示す半角スペースを置く（機能的スペースとして許容。例:「停止指摘 / 任意指摘 / 範囲外指摘 分類」）。
- 全角スラッシュ「／」は対比表現にのみ許容し、列挙には使わない。
- 裸の欧文語（英数字のみの語。例: AI）と和文の間は半角スペース1つ。欧文字を含む複合語（例: PRレビュー・監査SA・ChatGPT連携のような和欧混在語）は和語として扱い、語境界にスペースを置かない。複合語の語境界、および助詞・句読点・全角記号との間にはスペースを置かない。和欧の判別が曖昧な語（AI側など）は、文書内の既存表記に合わせる。
- 対応・定義を示す「=」の前後にはスペースを置かない（例:「SA=サブエージェント」「プランSA=`plan.md`」）。
- セクション参照（§名）は和文として扱い、後続の和文・助詞との間にスペースを置かない（直前のコードスパンとの間はコードスパン規則に従う）。

### 領域4: 文体の型
- ロールプロンプト冒頭（役割セクションの第1項目）には「何をするか（責務）」を書く。「誰が使うか（利用経路）」は正本（`docs/orchestration-process.md`）側に置く。
- 文の箇条書きは終止形と句点で書く（「〜する。」「〜しない。」）。名詞列挙は句点なしの体言止めで書く。同一リスト内の同種項目間での文体不統一を禁止する（文項目は常に句点必須。定義文・注記を含む名詞列挙リストでは、項目種別の混在自体は許容する）。
- 述語を省略した体言止め+句点の項目（「〜なら停止。」等）は文項目として扱う（句点必須・文項目と同種）。
- ロールプロンプトの標準セクション順は、役割→入力→ルール→出力を基本骨格とし、固有セクションはその間に置く（推奨）。

### 領域5: 新語・新文書追加時の手続き（再発防止）
- 新しい用語・略語・表記・文書をAI制御文書に導入する場合、先に本ポリシーの用語集・規則を更新し、その後に使用する（ポリシー更新が先、使用が後）。
- 本ポリシーに載らない新語の使用は、AI制御文書変更の監査・レビューで指摘対象とする。

### 領域6: 自己完結性・内容境界の規則
- 6-1. ロールプロンプトが持ってよい知識（限定列挙）:
  1. 自分の責務・禁止操作・停止条件
  2. 自分への入力の形式と前提条件（入力に他SAの成果物が含まれる場合、その成果物の形式・前提条件を記述してよい）
  3. 自分の出力の形式（出力フィールド名を含む。宛先は記述しない）
  4. 自分が読んでよいリポジトリ文書の限定列挙と読取条件
  5. 自分の判定基準で使用する分類名とその定義（自分が産出する分類に限る）
- 6-2. ロールプロンプトが持ってはならない知識:
  1. 他SAの責務・役割の定義（役割差別化は「自分がしないこと」の自己境界として書く）
  2. 自分・他SAの起動順序・起動条件（順序保証が必要な場合は、入力の前提条件として表現する）
  3. ループ制御・回数管理・完了判定・自動修正の成立条件の定義（ロールプロンプトは、所見・候補性を出力フィールドとして返すに留める）
  4. 他SAのロールプロンプトのパス（プランSAの例外は6-3に定める）
  5. 自分が産出しない分類体系の定義（混入禁止ルールに必要な範囲での分類名への言及のみ許容する）
- 6-3. 例外:
  - プランSA（`plan.md`）は指示書の設計者として、指示書テンプレート知識（各SAへ渡す内容の項目名・他SAロールプロンプトのパス・全SA分類の定義・停止条件 / ループ条件の設計材料）を保持してよい。他SAの責務定義そのものは保持しない。
  - `AGENTS.md` は親エージェント向け契約であり、全SAの起動順序・分類管理・完了判定の知識を持つことが責務である。SA内部の作業手順詳細は持たない。
- 6-4. 他文書参照の作法:
  - ロールプロンプトは、内容の委譲を目的とした `docs/orchestration-process.md` / `docs/prompt-guide.md` への参照（「詳細は〜を参照」型）を持たない（自己完結原則）。ただし、6-1の4の読取対象の限定列挙として、読取条件付きで特定セクション（例: `docs/prompt-guide.md` §書き味ポリシー）を参照する場合を除く。
  - リポジトリ文書（正本ドキュメント）への参照は、6-1の4「自分が読んでよいリポジトリ文書の限定列挙と読取条件」としてのみ持つ。
  - 越境知識をロールプロンプトに追加したくなった場合、まず「入力の前提条件」「出力フィールド」「自己境界」のいずれかへ変換できないか確認する。
- 6-5. 他工程の参照語彙:
  - ロールプロンプトは他工程を工程名（実装工程 / 契約準拠の判定工程 / 品質確認工程）で参照し、役割名（実装SA / 監査SA / レビューSA）を使わない。役割名は調整主体向け文書（`AGENTS.md` / `docs/orchestration-process.md`）の語彙である。
